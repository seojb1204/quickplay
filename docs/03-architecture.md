# 공통 시스템 아키텍처

```
packages/shared   규칙 엔진(순수 함수) · 게임 카탈로그 · 통신 자료형 · 시드 난수
apps/server       Fastify(HTTP) + Socket.IO(실시간) — 방·매칭·경기 진행·결과 저장
apps/web          React + Vite — 화면, 솔로 게임 실행, 대전 화면
e2e               Playwright(브라우저 2개로 실제 대전)
```

## 핵심 설계
1. **규칙은 한 곳(shared)에만**: 서버 판정과 브라우저 솔로 플레이가 같은 코드를 쓴다 → 규칙 불일치 방지.
2. **게임 3유형 = 서버 모듈 3패턴**
   - 실시간(패들): 서버가 물리 시뮬레이션, 클라이언트는 입력만 보냄.
   - 턴제(오목): 서버가 차례·유효 수·승패 판정, 한 수 타이머.
   - 기록 경쟁(뱀): 클라이언트가 같은 시드로 플레이, 서버가 입력 기록을 재생해 점수 계산.
3. **공통 허브(hub.ts)**: 방 생성·참여, 랜덤 대기열, 준비·카운트다운, 기권·연결 끊김·재접속, 결과 1회 확정·저장. 게임 모듈은 `ServerGameModule { create(ctx) → { action, snapshot } }` 만 구현.
4. **새 게임 추가** = shared 규칙 + 서버 모듈 1개 + 웹 Solo/Versus 컴포넌트 + 등록부 2곳(`apps/server/src/games/registry.ts`, `apps/web/src/games/registry.ts`). 매칭·저장·결과 화면은 재사용.
5. **상태 저장**: 방·대기열은 서버 메모리(단일 서버 전제). 결과만 DB.

## 단일 서버 전제와 확장 경로
- 지금은 서버 1대가 방·매칭을 모두 메모리에서 관리 → 가장 단순·저렴.
- 한계: 서버 재시작 시 진행 중 경기 유실, 수평 확장 불가.
- 확장 순서(실측 병목이 보일 때): ① 인스턴스 사양 상향 ② 게임별/지역별 서버 분리 ③ Redis 어댑터 + 방 위치 라우팅.

## 기술 선택 (우선 검토안 대비)
| 영역 | 검토안 | 채택 | 이유 |
|---|---|---|---|
| UI | React+TS+Vite | 채택 | — |
| 실시간 2D | Phaser | **보류 → Canvas 2D 직접** | 현재 3종은 Canvas 로 충분, 번들 +1MB 회피. 폭탄 미로·탱크 등 스프라이트·충돌이 복잡한 게임에서 재검토 |
| 서버 | Fastify | 채택 | — |
| 실시간 통신 | Socket.IO | 채택 | 재접속·방 브로드캐스트 기본 제공 |
| DB | PostgreSQL/Neon | 채택 | 로컬·CI 는 PostgreSQL 16, 미설정 시 메모리 저장소 |
| 인증 | Better Auth 등 | **미구현** | 로그인 방식 미결(D1). 비회원은 HMAC 서명 토큰 |
| 테스트 | Vitest·Playwright | 채택 | — |
| 배포 | Cloudflare Pages + Render | **Render 1개로 웹+서버 같이 제공 권장** | 같은 출처라 CORS·쿠키 문제 없음, 서비스 1개만 관리. 트래픽 늘면 정적 파일만 Cloudflare 로 분리 |
